# Data model

Phase 1 tables: users, projects, provider keys, gateway keys, and the log tables (created in GW-014, filled from Phase 3). Later tables are sketched at the end so we know where they attach.

## Overview

```
 auth schema (Better Auth owns)     app schema (we own)

 ┌─────────┐ 1          many ┌───────────┐ 1        0..1 ┌───────────────┐
 │  users  │────────────────<│ projects  │───────────────│ provider_keys │
 └────┬────┘                 └─────┬─────┘               └───────────────┘
      ├──< sessions                │ 1
      ├──< accounts                │
      └    verifications           │ many
                             ┌─────▼────────┐
                             │ gateway_keys │
                             └──────────────┘

 logs schema (Phase 3): request_logs, rollups. Copies IDs; no foreign keys (ADR 0007).
```

Read `──<` as "one to many".

## Conventions

| Topic | Rule | Why |
|---|---|---|
| Postgres schemas | `auth` (Better Auth), `app` (ours), `logs` (ADR 0007) | Clear ownership; logs can move out later |
| Names | `snake_case`, plural tables (`gateway_keys`) | Postgres norm; Better Auth `usePlural: true` matches |
| IDs | `uuid`, default `gen_random_uuid()` | Not guessable in URLs; built into Postgres 17 |
| Timestamps | `timestamptz`, UTC; `created_at` and `updated_at` on every table | Avoids timezone bugs |
| Fixed value lists | `text` + `CHECK` constraint | Easier to change than Postgres `enum` types |
| Rules | Enforced by the database (`NOT NULL`, `UNIQUE`, `CHECK`, foreign keys), not only in code | A bug in one app can't break the data |
| Deletes | Hard delete with `CASCADE`, except gateway keys (revoked, kept) | Simple; see Delete behaviour |

## Tables

### `auth.*`: Better Auth

Generated by `npx auth generate` from our auth config, then committed. We don't edit them by hand; regenerate when the config changes.

| Table | Holds | Key columns |
|---|---|---|
| `users` | One row per dashboard user | `id`, `name`, `email` (unique), `email_verified`, `image` |
| `sessions` | Logged-in sessions | `user_id` → users, `token` (unique), `expires_at`, `ip_address`, `user_agent` |
| `accounts` | Login methods per user | `user_id` → users, `provider_id` (`credential` for email + password), `password` (hash) |
| `verifications` | Short-lived tokens (email verify, reset) | `identifier`, `value`, `expires_at` |

Config needed: `usePlural: true`, `schemaName: "auth"`, `generateId: "uuid"`. Passwords: Better Auth's default hash, **scrypt** (see PITFALLS.md: Gateway keys use a fast hash).

### `app.projects`

A project groups one provider key and its gateway keys. Budgets and limits attach here later.

| Column | Type | Null | Default | Notes |
|---|---|---|---|---|
| `id` | `uuid` | no | `gen_random_uuid()` | Primary key |
| `owner_id` | `uuid` | no | | → `auth.users.id`, `ON DELETE CASCADE` |
| `name` | `text` | no | | 1–100 chars (`CHECK`) |
| `created_at` | `timestamptz` | no | `now()` | |
| `updated_at` | `timestamptz` | no | `now()` | Set by the app on update |

- `UNIQUE (owner_id, name)`: no two projects with the same name per user. Also serves as the index for "list my projects".

### `app.provider_keys`

The user's own provider key (BYOK), encrypted. One per project.

| Column | Type | Null | Default | Notes |
|---|---|---|---|---|
| `id` | `uuid` | no | `gen_random_uuid()` | Primary key |
| `project_id` | `uuid` | no | | → `projects.id`, `ON DELETE CASCADE`; `UNIQUE` (one per project) |
| `provider` | `text` | no | | `CHECK (provider IN ('openai'))` |
| `ciphertext` | `bytea` | no | | AES-GCM output |
| `nonce` | `bytea` | no | | 12 bytes, fresh per encryption (`CHECK`) |
| `auth_tag` | `bytea` | no | | 16 bytes; detects tampering (`CHECK`) |
| `master_key_version` | `smallint` | no | `1` | Which master key encrypted it; allows key rotation |
| `last_four` | `text` | no | | Last 4 chars, shown as `sk-…abcd` |
| `created_at` | `timestamptz` | no | `now()` | |
| `updated_at` | `timestamptz` | no | `now()` | |

- "Replace" updates the row in place (new nonce every time).
- Encryption uses `project_id` as AES-GCM additional data, so a ciphertext copied into another project's row fails to decrypt (GW-015). See PITFALLS.md: Provider key bound to its project.
- Second provider later: change `UNIQUE (project_id)` to `UNIQUE (project_id, provider)` and add to the `CHECK`. No table redesign.

### `app.gateway_keys`

Keys our users' apps send to the gateway (`gw_live_…`). Only a hash is stored.

| Column | Type | Null | Default | Notes |
|---|---|---|---|---|
| `id` | `uuid` | no | `gen_random_uuid()` | Primary key |
| `project_id` | `uuid` | no | | → `projects.id`, `ON DELETE CASCADE`; indexed |
| `name` | `text` | no | | Label, e.g. "prod server"; 1–100 chars |
| `key_hash` | `bytea` | no | | SHA-256 of the full key, 32 bytes; `UNIQUE` (hot-path lookup) |
| `key_prefix` | `text` | no | | First 12 chars, e.g. `gw_live_a1b2`, for display |
| `revoked_at` | `timestamptz` | yes | | `NULL` = active |
| `created_at` | `timestamptz` | no | `now()` | |
| `updated_at` | `timestamptz` | no | `now()` | |

- Hot-path lookup: `WHERE key_hash = $1` → `project_id`, `revoked_at`. Cached in Redis.
- Revoke sets `revoked_at`; the row stays so spend history can still show the key's name.
- `last_used_at` comes later (Phase 3), written by the worker, never the gateway.

### `logs.*`: request logs and usage rollups

One row per gateway request, written by the worker (never the gateway). Read and written only through the log store interfaces (ADR 0007). No foreign keys to `app` (see PITFALLS.md: No foreign keys into the logs schema).

**Never stored:** prompts, responses, provider error messages (see PITFALLS.md: Provider error messages can contain prompts). Opt-in prompt logging (later) gets its own table with its own retention.

#### `logs.request_logs`

| Column | Type | Null | Default | Notes |
|---|---|---|---|---|
| `request_id` | `uuid` | no | | UUID v7, made by the gateway; also sent to the client as `x-request-id` (see PITFALLS.md: UUID v7 for request logs) |
| `started_at` | `timestamptz` | no | | When the gateway received the request |
| `project_id` | `uuid` | no | | Copied, no foreign key |
| `gateway_key_id` | `uuid` | no | | Copied, no foreign key |
| `provider` | `text` | no | | e.g. `openai` |
| `model` | `text` | no | | Model the client asked for |
| `streamed` | `boolean` | no | | |
| `outcome` | `text` | no | | What happened. `CHECK`: `success`, `blocked`, `provider_error`, `gateway_error`, `client_disconnected` |
| `reason` | `text` | yes | | Why, as a short code (see Reasons). Required unless `success` or `client_disconnected` (`CHECK`) |
| `status_code` | `smallint` | no | | HTTP status sent to the client |
| `input_tokens` | `integer` | no | `0` | From the provider's response |
| `cached_input_tokens` | `integer` | no | `0` | Part of `input_tokens` the provider bills cheaper (prompt caching) |
| `output_tokens` | `integer` | no | `0` | |
| `usage_source` | `text` | no | | `CHECK`: `provider` (exact), `estimated` (disconnect, no usage sent), `none` |
| `input_cost_nanos` | `bigint` | no | `0` | Cost in nano-dollars (1 = $0.000000001), price valid at `started_at` (see PITFALLS.md: Money in nano-dollars) |
| `output_cost_nanos` | `bigint` | no | `0` | |
| `duration_ms` | `integer` | no | | Received → last byte sent |
| `ttft_ms` | `integer` | yes | | Time to first token (streaming only) |
| `gateway_overhead_ms` | `integer` | no | | Our own time before forwarding (auth, limits); feeds the README p95 |

- `PRIMARY KEY (request_id, started_at)`: a retried job inserts the same row again, and `ON CONFLICT DO NOTHING` drops the copy. `started_at` is in the key so monthly partitions can be added later without changing it (Postgres requires the partition column in every unique key).
- Index `(project_id, started_at DESC)`: "recent requests" lists and rollup rebuilds.
- BRIN index on `started_at`: a tiny index for time-ordered tables; makes the retention delete cheap.
- Requests with a bad gateway key (`401`) are not logged: there is no project to attach them to.
- Blocked requests are logged with their `reason`, 0 tokens, 0 cost and `usage_source = none`.
- Not partitioned in v1; see [roadmap](../planning/roadmap.md#professional-nice-to-haves).

**Reasons** (`CHECK` list; the blocked ones are confirmed when limits are built in Phase 2):

| Outcome | `reason` | Means | Dashboard shows |
|---|---|---|---|
| `blocked` | `rate_limit_requests` | Too many requests per minute | "Rate limit: requests per minute" |
| `blocked` | `rate_limit_tokens` | Too many tokens per minute | "Rate limit: tokens per minute" |
| `blocked` | `in_flight_limit` | Spend ≥ 90%, too many requests at once (ADR 0006) | "Throttled: near budget" |
| `blocked` | `budget_cap_reached` | Spend ≥ 100% of the monthly cap | "Budget reached" |
| `blocked` | `budget_reservation_exceeded` | This request's max cost doesn't fit in what's left | "Request too large for remaining budget" |
| `blocked` | `input_too_large` | Input over the length limit | "Input too long" |
| `provider_error` | `provider_auth_failed` | Provider rejected the user's provider key | "Your provider key was rejected" |
| `provider_error` | `provider_rate_limited` | Provider's own rate limit on the user's account | "Provider rate limit" |
| `provider_error` | `provider_bad_request` | Provider returned 400 | "Provider rejected the request" |
| `provider_error` | `provider_server_error` | Provider returned 5xx | "Provider error" |
| `provider_error` | `provider_timeout` | No response in time | "Provider timed out" |
| `gateway_error` | `provider_key_unreadable` | Stored provider key failed to decrypt | "Re-enter your provider key" |
| `gateway_error` | `internal` | Bug on our side | "Gateway error" |

#### `logs.usage_hourly`

Pre-summed usage per project, key, model and hour. The dashboard reads this, not raw logs.

| Column | Type | Null | Notes |
|---|---|---|---|
| `hour` | `timestamptz` | no | Start of the hour, UTC |
| `project_id` | `uuid` | no | |
| `gateway_key_id` | `uuid` | no | |
| `model` | `text` | no | |
| `request_count` | `integer` | no | |
| `error_count` | `integer` | no | Outcomes `provider_error`, `gateway_error` |
| `blocked_count` | `integer` | no | Outcome `blocked` |
| `input_tokens`, `cached_input_tokens`, `output_tokens` | `bigint` | no | Sums |
| `input_cost_nanos`, `output_cost_nanos` | `bigint` | no | Sums |
| `duration_ms_sum` | `bigint` | no | Average latency = sum ÷ `request_count` |

- `PRIMARY KEY (project_id, hour, gateway_key_id, model)`.
- **Built by recomputing, not adding.** After inserting a batch, the worker recomputes every (project, hour) the batch touched from `request_logs` and overwrites those rollup rows. Retries, duplicates and late rows can't double-count.
- Percentiles (p95) can't be summed from rollups. p95 comes from raw logs, within retention (see PITFALLS.md: Percentiles don't add up).
- No daily table: the dashboard adds up hours into days in the viewer's timezone (see PITFALLS.md: Daily totals depend on timezone).
- Breakdown by `reason` comes from raw logs (last 90 days).
- **Retention:** raw logs 90 days (daily job), rollups forever.

#### Log store interfaces

Split by who uses them (interface segregation):

| Interface | Used by | Methods |
|---|---|---|
| `RequestLogWriter` | Worker | `insertRequestLogs(rows)` (skips duplicates), `rebuildHourlyUsage(projectId, hours)` |
| `UsageReader` | Admin API | `getUsage({ projectId, from, to, groupBy })`, `listRequests({ projectId, cursor, limit })` |
| `LogRetention` | Worker (daily job) | `deleteRequestLogsBefore(date)` (in small batches) |

The gateway uses none of them: it only enqueues a log job.

## Delete behaviour

| Deleted | Database does | App must also do |
|---|---|---|
| User | Cascades to sessions, accounts, projects, and from projects to keys | Clear Redis cache for all their gateway keys |
| Project | Cascades to its provider key and gateway keys | Clear Redis cache for its gateway keys |
| Gateway key | Never deleted; `revoked_at` is set | Clear its Redis cache entry |

A database cascade can't reach Redis. So deletes go through app code that also clears the cache, never a bare SQL delete. See PITFALLS.md: Cascades don't reach Redis.

## How SOLID applies

SOLID is a set of five rules for code (classes and modules). Tables aren't code, so two rules have a direct match in the schema and all five apply to the code that reads and writes it (`packages/db`).

### In the schema

| Rule | Meaning | Here |
|---|---|---|
| **S**ingle responsibility | One thing, one reason to change | Each table is one concept. Budgets get their own table later instead of more columns on `projects`. Better Auth's tables and ours live in separate schemas. |
| **O**pen/closed | Add new things without changing old ones | New features add tables that point at `projects`. A second provider is a constraint change, not a redesign. |

### In the access layer (`packages/db`)

| Rule | Here |
|---|---|
| **S**ingle responsibility | One repository (data-access module) per table group: projects, provider keys, gateway keys. Repositories store and load bytes; they never encrypt. Crypto lives in `shared`; app services combine the two. |
| **O**pen/closed | A new store (e.g. a dedicated log DB) is a new implementation of an existing interface; callers don't change. |
| **L**iskov substitution | Each interface has one shared test suite. Every implementation must pass it, so any one can stand in for another. |
| **I**nterface segregation | Interfaces are shaped by who uses them. The gateway gets `findGatewayKeyByHash` only; the admin API gets create, list, revoke. |
| **D**ependency inversion | Apps depend on interfaces, not on Drizzle. The real implementations are wired in once at startup. No dependency-injection framework. |

Tenancy (users only see their own data) goes through one function, `canAccessProject(userId, projectId)`. No query checks `owner_id` on its own, so moving to teams changes only that function ([ADR 0011](../decisions/0011-project-ownership.md)).

| # | Question | Decision |

| 14 | `request_id` type | UUID v7, made by the gateway |
