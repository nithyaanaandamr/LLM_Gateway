# @gw/db

- **Layer:** Package (schema, client, repositories)
- **May import:** `drizzle-orm`, `pg`, `@gw/shared` (nothing yet)
- **Does not:** import `@gw/auth`, apps or HTTP frameworks

Drizzle schema, migrations and the database client.

- App data: users, projects, provider keys, gateway keys, model pricing
- Logs: request logs and rollups, in a separate `logs` schema, accessed only through the `LogStore` interface (see [ADR 0007](../../docs/decisions/0007-log-store-separation.md))

## Layout

- `src/schema/`:
  - `auth.ts`: generated by `pnpm auth:generate`; never edit
  - `app.ts`: app tables
  - `logs.ts`: not exported; only the LogStore uses it (ADR 0007)
  - `columns.ts`: shared column helpers
  - `postgres-schemas.ts`: the Postgres schemas
- `migrations/`: generated SQL, committed
- `src/client.ts`: `createDb(url)`
- `src/migrate.ts`: `runMigrations(url)`
- `src/repositories/`: queries (see Repositories)
- `src/unique-violation.ts`: `isUniqueViolation(error, constraint)`, for turning a duplicate into a 409
- `src/testing/`: test-only helpers, exported as `@gw/db/testing`
- `dist/`: compiled output (git-ignored; `pnpm build`)

## Repositories

Plain functions in `src/repositories/` that take `db` and load or store rows. They never encrypt (services in the apps combine the two). Apps never import `drizzle-orm` at runtime, so every query goes through these.

- `gateway-keys.ts`: `insertGatewayKeyWithinLimit` (exact cap, per project), `listGatewayKeys` (newest first), `countActiveGatewayKeys`, `revokeGatewayKey` (matches `id` and `project_id`, idempotent); takes a hash and prefix, never a key
- `projects.ts`: `listAccessibleProjects` (sorted by bytes, whatever the collation), `findAccessibleProject`, `countAccessibleProjects`, `insertProjectWithinLimit`, `renameProject`, `deleteProject`; re-exports `insertProject` and `isProjectNameTaken` from `insert-project.ts`
- `provider-keys.ts`: `upsertProviderKey` (one atomic upsert; a replace keeps `id` and `createdAt`), `findProviderKeySummary`, `deleteProviderKey`. Reads return only `provider`, `lastFour` and the dates, never the encrypted columns. The caller encrypts; this file stores the bytes

**Project access.** `project-access.ts` exports `accessibleProjects(userId)`, a SQL condition (today `owner_id = userId`). It is the only code that reads `owner_id` to decide access ([ADR 0011](../../docs/decisions/0011-project-ownership.md)); a test pins that only `project-access.ts` and `insert-project.ts` (the one writer) name it, in this package and in admin-api. It is not exported from the package. Use `findAccessibleProject` or `listAccessibleProjects`: one query checks access and loads the row, and "someone else's" and "missing" both come back as `undefined`. `renameProject` and `deleteProject` take the user ID and apply the same condition, so they are safe even without a prior `findAccessibleProject`.

**Exact limits.** A cap (100 projects per user, 20 active gateway keys per project) is counted and inserted in one transaction that first takes a lock, so parallel requests can't overshoot ([ADR 0013](../../docs/decisions/0013-atomic-limits.md)).
- `limit-lock.ts` exports `lockForLimit(tx, scope, id)`: a Postgres advisory lock (`pg_advisory_xact_lock`) named by `(scope, id)`, held until the transaction ends (commit, rollback or a dead connection). Requests with the same `(scope, id)` take turns; others don't wait. It is generic: projects use `("projects", userId)`, gateway keys (GW-020) will use `("gateway-keys", projectId)`. Not exported from the package.
- Pattern: `db.transaction(async (tx) => { await lockForLimit(tx, scope, id); count; insert })`. See `insertProjectWithinLimit`, which returns `{ status: "created", project }` or `{ status: "limit_reached" }`. A duplicate name still throws; `isProjectNameTaken(error)` recognises it.
- The lock holds a pooled connection while it waits (PITFALLS.md: Lock waits share the database pool).

**`Transaction` and `Queryable`** (`client.ts`): `Transaction` is what a `db.transaction` callback receives; `Queryable` is `Database | Transaction`. Repository functions that must work both alone and inside a cap transaction (`insertProject`, `countAccessibleProjects`) take a `Queryable`.

Name repository functions after their table (`insertGatewayKey`, not `insert`): the index does `export *` from each file, and two equal names are a TypeScript error.

## Add a migration

1. Edit `src/schema/` (for auth tables: change `packages/auth` and run `pnpm auth:generate`).
2. `pnpm db:generate --name <what_changed>`
3. Read the SQL, then commit it.

Never edit a migration that has been merged; add a new one.

## Run migrations

```sh
pnpm infra:up
cp .env.example .env   # first time only
pnpm db:migrate
```

## Use the test harness in another package

1. Add `@gw/db` as a workspace dependency.
2. Create `vitest.global-setup.ts`:
   ```ts
   import { setupTestPostgres } from "@gw/db/testing";
   export default setupTestPostgres;
   ```
3. In `vitest.config.ts`: `defineConfig({ test: { globalSetup: ["./vitest.global-setup.ts"] } })`.
4. In a test file:
   ```ts
   let connection: DbConnection;
   beforeAll(async () => {
     connection = createDb(await createTestDatabase());
   });
   afterAll(() => connection.close());
   ```

Each test file gets its own migrated database. Also add `{ "path": "../../packages/db/tsconfig.build.json" }` to the consuming package's `tsconfig.build.json` references, so `tsc -b` builds `@gw/db` first.
